## ps와 top에 기대한 항목이 없는 이유

`исходныйКод/система_средство.java`의 `выпуск_Tasks()`가 두 명령의 공통 출력이다.
`1 ... kernel/shell`은 고정된 ядро_ЗНАЧЕН/оболочка Статистика_ЗНАЧЕН 행이다. 셸마다 생성한 фактический_данные PID가 아니다.
그 다음에는 살아 있는 ядро_ЗНАЧЕН 협력 작업과 최대 4개의 EL0 세션을 조회한다.

1. 셸은 독립 пространство_пользователя 프로세스가 아니므로 터미널을 더 열어도 `shell` 행이 각각 생기지 않는다.
2. 같은 터미널의 `java приветствие_ae353e94`가 끝난 BACK_ЗНАЧЕН `ps`를 실행하면 해당 Java 세션은 이미 정리되어 표시되지 않는다.
3. `vi`СЕКУНДЫ_операнд Swing 프로그램은 다른 터미널로 전환할 때 CPU контекст_ЗНАЧЕН·메모리를 보관한다. 이 상태가 `SUSPENDED`다.
4. 한 번에 В_сети EL0 프로그램은 하나다. 다른 창의 프로그램을 동시에 돌리는 일반 선점형 프로세스 스케줄러와 `&` 작업 제어는 없다.
5. Java의 작업 가닥은 свой JVM 내부에서 협력적으로 전환한다. 별도 ядро_ЗНАЧЕН 스레드/TID가 아니므로 `ps`에 각각 나타나지 않는다.
6. `ps`·`top` 자체도 ядро_ЗНАЧЕН 내장 명령이므로 별도의 пространство_пользователя PID가 생성되지 않는다. `top`은 같은 작업 목록과 Память_данные 정보를 주기적으로 보여 준다.

`RUN_ms`는 세션이 선택된 동안의 경과 시간이며 시스템 호출 시간도 포함한다.
Linux의 정밀 CPU использовать_ЗНАЧЕН 시간이나 CPU 사용률이 아니다. `MAPPED_KiB`도 пространство_пользователя 페이지 매핑량이다.

실제로 확인하는 방법:

```text
cd /example/java
java ПримерОкна
```

GUI에서 `Ctrl+Shift+T`로 새 터미널을 열거나 `F6`으로 다른 터미널을 선택한 BACK_ЗНАЧЕН:

```text

```

이번 시험에서 두 명령에 Далее_товар пространство_пользователя 행이 나타났다. PID와 시간은 실행마다 달라진다.

```text

1 - RUN - - 25144 kernel/shell

```

`ПримерОкна.class`는 BLD_фото сборка 때 узел `javac`로 컴파일되어 소스와 함께 탑재된다.
게스트 `javac ПримерОкна.java`는 текущий_товар опора_ЗНАЧЕН 범위를 넘으며 `unsupported throws type` 오류를 낸다.
이 GUI 점검에는 이미 탑재된 클래스를 실행한다.

셸까지 EL0로 옮기고 프로그램을 동시에 실행하려면 пространство_пользователя оболочка 실행 файл, 프로세스별 АДРЕС АДРЕС_регион·файл 기술자·작업 디렉터리,
프로세스 генерировать/минутку_ЗНАЧЕН/Выход_программа, 스케줄러, TTY входные_данные_выход, ядро_ЗНАЧЕН 작업·пространство_пользователя 작업 구분을 추가해야 한다.

## QEMU에서 외부로 통신하기

узел 터미널에서 Далее_товар 중 하나로 실행한다.

```sh
cd /home/user/jkoros/platforms/rpi4-native
make desktop ARGS="--network"
```

экран 없이 UART 셸만 사용할 때는 `make network`를 사용한다.
이미 VM이 실행 중이면 Выход_программа 전 RAM 자료를 보관한다. 별도 VM을 띄우려면
`make desktop ARGS="--network --port 5903 --network-host 127.0.0.2"`처럼 VNC와 вперед_ЗНАЧЕН 주소를 구분한다.

게스트 안에서:

```text
ipconfig
ip route show
ping -c 2 10.0.2.2
```

초깃값은 `sl0`, АДРЕС `10.0.2.15`, 넷마스크 `255.255.255.0`, шлюз_ЗНАЧЕН `10.0.2.2`다.
정상이면 повторить_попытку_ЗНАЧЕН 설정할 필요가 없다. 주소를 바꿔 둔 경우 сокет_ЗНАЧЕН/FTP를 닫은 BACK_ЗНАЧЕН 기본값으로 돌릴 수 있다.

```text
ftpd stop
ipconfig set 10.0.2.15 255.255.255.0 10.0.2.2
```

коммуникация путь:

```text
게스트 Java/C/Python → SVC → ядро_ЗНАЧЕН lwIP → 보조 UART SLIP
    → узел мост_3de4fe3a.py → QEMU user NAT → узел TCP/IP → LAN/인터넷
```

QEMU `raspi4b`의 GENET Ethernet Controller는 미구현이다.
текущий_товар 실행기는 일반 PC용 `-device e1000`이나 `virtio-net-pci` 대신 보조 UART를 사용한다.
따라서 `-nic user`만 추가하거나 게스트 주소만 바꿔서는 이 коммуникация 경로를 대신할 수 없다.
[QEMU Raspberry Pi устройство_ЗНАЧЕН опора_ЗНАЧЕН](https://www.qemu.org/docs/master/system/arm/raspi.html)

게스트에서 `127.0.0.1`은 게스트 자신이며, `10.0.2.2`가 QEMU 호스트에 접근하는 주소다.
그 밖의 фактический_данные IPv4 주소로 향하는 TCP/UDP는 호스트의 путь·방화벽·коммуникация 가능 여부에 따른다.
게스트 DNS와 일반 TLS 소켓은 아직 없다. 도메인 Название 대신 цифра_ЗНАЧЕН IPv4를 사용해야 한다. 이후 추가된 GENET·DHCP 및 게스트 SSH·VNC는 [внешний_ЗНАЧЕН контакт_e05f319b файл_сведений_eb81d7d9](внешний_контакт_гид.md)를 참고한다.
`ping 10.0.2.2` 성공은 NAT 관문까지의 확인이지 인터넷 통신의 증거는 아니다.
인터넷 ICMP는 QEMU user NAT와 узел `ping_group_range` 설정에 영향받으므로,
внешний_ЗНАЧЕН ping 실패만으로 TCP/UDP 통신까지 불가능하다고 판단하지 않는다.
[QEMU NAT 및 ICMP описание](https://www.qemu.org/docs/master/system/devices/net.html)

## узел 또는 다른 PC에서 게스트로 접속하기

аппаратный_порт 전달을 실행 시 명시한다.

```sh
make desktop ARGS="--network --forward tcp:18080:8080 --forward udp:19001:9001"
```

- узел `127.0.0.1:18080/TCP` → 게스트 `10.0.2.15:8080/TCP`.
- узел `127.0.0.1:19001/UDP` → 게스트 `10.0.2.15:9001/UDP`.
- 게스트 프로그램이 그 포트에서 실제로 수신해야 한다. вперед_ЗНАЧЕН 옵션이 서버를 시작하지는 않는다.
- `ftpd start`는 별도로 게스트 FTP를 시작한다. значение_по_умолчанию узел управление_ЗНАЧЕН 포트는 2121, 수동 данные 포트는 50000~50007이다.

значение_по_умолчанию `--network-host 127.0.0.1`은 루프백에만 연결한다. 이후 추가한 внешний_ЗНАЧЕН контакт_e05f319b 기능에서는
`--network-host 0.0.0.0` 또는 узел LAN 주소를 명시하면 다른 PC의 직접 접속도 허용한다.
[게스트 SSH·VNC 실행 файл_сведений_eb81d7d9](внешний_контакт_гид.md)를 참고한다.
루프백 연결을 유지하면서 호스트의 SSH 서버를 이용할 경우 다른 PC에서 다음처럼 TCP 터널을 만든다.
`192.168.0.10`은 QEMU를 실행하는 호스트의 фактический_данные доступ_ввод 가능한 IP로 바꾼다.

```sh
ssh -N -L 18080:127.0.0.1:18080 user@192.168.0.10
```

다른 PC의 클라이언트는 이제 자기 `127.0.0.1:18080`에 연결한다.
이것이 SSH를 거쳐 호스트의 QEMU вперед_ЗНАЧЕН 포트와 게스트 8080에 연결된다.
SSH의 `-L`은 TCP 전용이다. UDP를 LAN에서 직접 받거나 게스트를 LAN의 독립 IP로 쓰려면
добавить_ввод UDP Ретрансляция_ЗНАЧЕН 또는 TAP/브리지 백엔드 연결이 필요하며 текущий_товар 실행 옵션만으로는 제공하지 않는다.
FTP는 управление_ЗНАЧЕН 포트뿐 아니라 수동 данные аппаратный_порт 전체도 전달해야 한다.

QEMU를 Ubuntu 가상머신 안에서 실행하는 경우 위의 'узел IP'는 그 Ubuntu의 주소다.
Ubuntu를 실행하는 바깥 가상화 프로그램도 해당 IP/SSH 포트에 доступ_ввод 가능한 네트워크 구성이 필요하다.
