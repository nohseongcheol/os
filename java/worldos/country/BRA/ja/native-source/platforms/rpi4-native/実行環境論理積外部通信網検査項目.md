# 内蔵 ARM64 커널의 命令実行 階層値·프로세스 値表示·QEMU 外部値 通信

2026-10-04 状況調査. 대상은 `jkoros/platforms/rpi4-native`의 内蔵 Java 커널이다.
`platforms/rpi4`의 Linux/OpenJDK 판이나 `os`의 기존 x86 판에 이 결과를 적용하지 않는다.

## 命令実行 階層値

| 対象値 | 命令実行 位置 | 現在項目 実装 |
|---|---|---|
| シェル, `sh` スクリプト値, `ps`, `top`, ファイル 내장 命令 | EL1 中核値 | Java AOT 中核値 함수로 呼出 |
| 端末 창과 シェル 状況値 | 中核値 | 最大値 4개의 상태를 値保持·복원; 독립 シェル 프로세스가 아님 |
| `java`, `javac` | EL0 利用者 領域値 | `java-tools.elf`를 적재하고 별도 利用者 被演算子スタック·페이지 권한으로 命令実行 |
| `java CLASS`, `java -jar`의 プログラム | EL0의 内蔵 JVM 내부 | バイトコード 命令実行. 전체 OpenJDK가 아님 |
| `jaot` 結果 ELF | EL0 | 지원되는 부분집합을 ARM64 코드로 컴파일한 後続側状況 ELF로 命令実行 |
| `python`, `vi`, `cc`, 利用者 ELF | EL0 | 利用者 命令実行 ファイル 적재 経路 使用値 |
| ファイル·ソケット値·그래픽 시스템 呼出 | EL1 | EL0에서 SVC로 들어와 처리한 後端値 利用者 프로그램으로 복귀 |

근거:

- `ソース/命令解釈器.java`: `道具要素入口()` 및 `java`/`javac` 命令 分岐.
- `機械/利用者.c`: `プログラム起動処理()`의 ELF 적재, 페이지 許可値 設定値, PID 배정, `利用者入場()`.
- `起動/入口点値.S`: `user_enter`의 `SP_EL0`, `SPSR_EL1=0x340`, `eret`.
- `ソース/窓セッション.java`: 네 터미널의 シェル 상태와 利用者 세션 値保持·再開実行状態.

QEMU QMP로 CPU 0을 実際データ 정지하여 읽은 許可値 상태는 シェル 値待合 중 `EL1h`, Java 計算結果 중 `EL0t`였다.
이 결과는 소스의 주석이나 出力 문자열만으로 판정한 것이 아니다.

## ps와 top에 기대한 항목이 없는 理由値

`ソース/システム道具要素.java`의 `作業一覧表示()`先頭位置被演算子 두 명령의 共通値 출력이다.
`1 ... kernel/shell`은 고정된 中核値/シェル 統計値 행이다. 셸마다 생성한 実際データ PID가 아니다.
그 다음에는 살아 있는 中核値 협력 작업과 最大値 4개의 EL0 세션을 조회한다.

1. 셸은 독립 利用者 프로세스가 아니므로 터미널을 더 열어도 `shell` 행이 각각 생기지 않는다.
2. 같은 터미널의 `java 挨拶例`先頭位置被演算子 끝난 後端値 `ps`를 실행하면 해당 Java 세션은 이미 정리되어 표시되지 않는다.
3. `vi`第二被演算子 Swing 프로그램은 다른 터미널로 전환할 때 CPU 文脈値·메모리를 보관한다. 이 상태가 `SUSPENDED`第三被演算子.
4. 한 번에 活動中 EL0 프로그램은 하나다. 다른 창의 프로그램을 동시에 돌리는 일반 선점형 프로세스 스케줄러와 `&` 作業 제어는 없다.
5. Java의 作業 가닥은 内蔵 JVM 내부에서 협력적으로 전환한다. 별도 中核値 스레드/TID가 아니므로 `ps`에 각각 나타나지 않는다.
6. `ps`·`top` 자체도 中核値 내장 명령이므로 별도의 利用者 PID가 생성되지 않는다. `top`은 같은 作業 목록과 記憶データ 정보를 주기적으로 보여 준다.

`RUN_ms`는 세션이 선택된 동안의 경과 시간이며 시스템 呼出 시간도 포함한다.
Linux의 정밀 CPU 使用値 시간이나 CPU 사용률이 아니다. `MAPPED_KiB`도 利用者 페이지 매핑량이다.

실제로 확인하는 방법:

```text
cd /example/java
java 窓例
```

GUI에서 `Ctrl+Shift+T`로 새 터미널을 열거나 `F6`으로 다른 터미널을 선택한 後端値:

```text
ps
top -n 1
```

이번 시험에서 두 명령에 次回項目 利用者 행이 나타났다. PID와 시간은 실행마다 달라진다.

```text
PID SLOT STATE MAPPED_KiB RUN_ms AGE_ms COMMAND
1 - RUN - - 25144 kernel/shell
24 0 SUSPENDED 9608 507 3960 java 窓例
```

`窓例.class`는 イメージ構築 システム構築 때 ホスト `javac`로 컴파일되어 소스와 함께 탑재된다.
게스트 `javac 窓例.java`는 現在項目 支援値 범위를 넘으며 `unsupported throws type` 오류를 낸다.
이 GUI 점검에는 이미 탑재된 클래스를 실행한다.

셸까지 EL0로 옮기고 프로그램을 동시에 실행하려면 利用者 シェル 命令実行 ファイル, 프로세스별 番地 番地領域·ファイル 기술자·作業 디렉터리,
프로세스 生成/値待合/終了点プログラム, 스케줄러, TTY 入力出力, 中核値 作業·利用者 作業 구분을 추가해야 한다.
`ps` 출력에 이름만 추가해서는 利用者 許可値 분리나 동시 실행이 구현되지 않는다.

## QEMU에서 외부로 통신하기

ホスト 터미널에서 次回項目 중 하나로 실행한다.

```sh
cd /home/user/jkoros/platforms/rpi4-native
make desktop ARGS="--network"
```

画面 없이 UART 셸만 사용할 때는 `make network`를 사용한다.
이미 VM이 命令実行 중이면 終了点プログラム 直前側値 RAM 자료를 보관한다. 별도 VM을 띄우려면
`make desktop ARGS="--network --port 5903 --network-host 127.0.0.2"`처럼 VNC와 前方値 주소를 구분한다.

게스트 안에서:

```text
ipconfig
ip route show
ping -c 2 10.0.2.2
```

초깃값은 `sl0`, 番地 `10.0.2.15`, 넷마스크 `255.255.255.0`, 中継門値 `10.0.2.2`第三被演算子.
정상이면 再試行処理値 설정할 필요가 없다. 주소를 바꿔 둔 경우 ソケット値/FTP를 닫은 後端値 기본값으로 돌릴 数 있다.

```text
ftpd stop
ipconfig set 10.0.2.15 255.255.255.0 10.0.2.2
```

通信 経路:

```text
게스트 Java/C/Python → SVC → 中核値 lwIP → 補助値 UART SLIP
    → ホスト 通信網橋渡し.py → QEMU user NAT → ホスト TCP/IP → LAN/인터넷
```

QEMU `raspi4b`의 GENET Ethernet Controller는 미구현이다.
現在項目 실행기는 일반 PC용 `-device e1000`이나 `virtio-net-pci` 대신 補助値 UART를 사용한다.
따라서 `-nic user`만 추가하거나 게스트 주소만 바꿔서는 이 通信 경로를 대신할 数 없다.
[QEMU Raspberry Pi 装置 支援値](https://www.qemu.org/docs/master/system/arm/raspi.html)

게스트에서 `127.0.0.1`은 게스트 자신이며, `10.0.2.2`先頭位置被演算子 QEMU 호스트에 접근하는 주소다.
그 밖의 実際データ IPv4 주소로 향하는 TCP/UDP는 호스트의 経路·방화벽·通信 가능 여부에 따른다.
게스트 DNS와 일반 TLS 소켓은 아직 없다. 도메인 名前 대신 桁値 IPv4를 사용해야 한다. 後続側値 추가된 GENET·DHCP 및 게스트 SSH·VNC는 [外部値 接続状態 案内](外部接続状態手引.md)를 참고한다.
`ping 10.0.2.2` 성공은 NAT 관문까지의 확인이지 인터넷 통신의 증거는 아니다.
인터넷 ICMP는 QEMU user NAT와 ホスト `ping_group_range` 설정에 영향받으므로,
外部値 ping 실패만으로 TCP/UDP 통신까지 불가능하다고 판단하지 않는다.
[QEMU NAT 및 ICMP 説明](https://www.qemu.org/docs/master/system/devices/net.html)

## 実際データ TCP/UDP 왕복 用例

VM을 실행한 상태에서 호스트의 다른 터미널에서:

```sh
cd /home/user/jkoros/platforms/rpi4-native
python3 道具/復唱試験サーバー.py --tcp-port 9000 --udp-port 9001
```

게스트 안에서:

```text
cd /example/java
java 通信例 9000 9001
cd /example/python
python 通信例.py 9001
```

Java 예제는 TCP와 UDP, Python 예제는 UDP를 ホスト 응답기로 보내고 実際データ 받은 자료를 비교한다.
Java 예제의 클래스는 이미 탑재되어 있다. 이 예제의 値受取 제한은 700ms이므로 느린 호스트에서는
用例 자체의 時間値 제한을 조정해야 할 数 있다.

## ホスト 또는 다른 PC에서 게스트로 접속하기

機器ポート 전달을 命令実行 시 명시한다.

```sh
make desktop ARGS="--network --forward tcp:18080:8080 --forward udp:19001:9001"
```

- ホスト `127.0.0.1:18080/TCP` → 게스트 `10.0.2.15:8080/TCP`.
- ホスト `127.0.0.1:19001/UDP` → 게스트 `10.0.2.15:9001/UDP`.
- 게스트 프로그램이 그 포트에서 실제로 수신해야 한다. 前方値 옵션이 서버를 시작하지는 않는다.
- `ftpd start`는 별도로 게스트 FTP를 시작한다. 既定値 ホスト 制御値 포트는 2121, 수동 データ 포트는 50000~50007이다.

既定値 `--network-host 127.0.0.1`은 루프백에만 연결한다. 後続側値 추가한 外部値 接続状態 기능에서는
`--network-host 0.0.0.0` 또는 ホスト LAN 주소를 명시하면 다른 PC의 직접 접속도 허용한다.
[게스트 SSH·VNC 命令実行 案内](外部接続状態手引.md)를 참고한다.
루프백 연결을 유지하면서 호스트의 SSH 서버를 이용할 경우 다른 PC에서 다음처럼 TCP 터널을 만든다.
`192.168.0.10`은 QEMU를 실행하는 호스트의 実際データ アクセス入口 가능한 IP로 바꾼다.

```sh
ssh -N -L 18080:127.0.0.1:18080 user@192.168.0.10
```

다른 PC의 클라이언트는 이제 自身参照 `127.0.0.1:18080`에 연결한다.
이것이 SSH를 거쳐 호스트의 QEMU 前方値 포트와 게스트 8080에 연결된다.
SSH의 `-L`은 TCP 전용이다. UDP를 LAN에서 직접 받거나 게스트를 LAN의 독립 IP로 쓰려면
入口追記 UDP 値中継 또는 TAP/브리지 백엔드 연결이 필요하며 現在項目 命令実行 옵션만으로는 제공하지 않는다.
FTP는 制御値 포트뿐 아니라 수동 データ 機器ポート 전체도 전달해야 한다.

QEMU를 Ubuntu 가상머신 안에서 실행하는 경우 위의 'ホスト IP'는 그 Ubuntu의 주소다.
Ubuntu를 실행하는 바깥 가상화 프로그램도 해당 IP/SSH 포트에 アクセス入口 가능한 네트워크 구성이 필요하다.

## 状況調査 재현과 検証 切抜き

```sh
make test-layers
```

- QMP CPU 0 레지스터: シェル `EL1h`, Java 計算結果 `EL0t`.
- 종료된 Java 프로그램의 `ps` 入口値 入口除去.
- Java GUI의 다른 端末 切替方式 後続側状況 별도 PID 및 `SUSPENDED` 상태를 `ps`와 `top`에서 検証.
- 中継門値 ICMP 왕복, FTP クラス値 업로드.
- 독립 ホスト 상대와 TCP/UDP 발신, 명시적 機器ポート 전달을 통한 TCP/UDP 値受取 및 データ 비교.
- 終了点プログラム 시 이번 점검이 만든 QEMU만 清掃構築.

결과는 [보고서](build/verification/execution-network-review/report.json)와
[直列値 履歴記録値](build/verification/execution-network-review/serial.log)에 저장한다.
보고서에 사용한 中核値 SHA-256과 원시 QMP 레지스터를 남긴다.
최초 시도에서는 지원하지 않는 GUI 소스의 게스트 재컴파일 단계가 실패했고,
`initial-attempt-report.json`/`initial-attempt-serial.log`에 기록을 보관했다.
탑재된 GUI クラス値 사용으로 状況調査 절차를 수정한 後続側状況 上端値 항목은 全体構築 통과했다.

이번 実際データ 通信 검증의 범위는 **게스트와 QEMU 밖의 독립 ホスト プログラム 区切り**第三被演算子.
별도 물리 PC, 공인 인터넷 宛先通信端点, SSH 터널, 実際データ Pi 4 Ethernet에서의 송수신은 시험하지 않았다.
中核値 셸을 利用者 셸로 이식하거나 일반 프로세스 스케줄러를 추가한 변경은 아니다.
