# بومی ARM64 커널의 Codex نصب_مقدار 가능성 검토

검토일: 2026-10-05. 소스와 공식 문서를 대조한 설계 검토이며, 게스트에 Codex를 설치하거나
로그인·모델 호출을 실행한 결과는 아니다. بومی ARM64 커널과 `../rpi4` Linux 실행판은 구분한다.

현재 بومی 커널에는 공식 Codex CLI를 그대로 نصب_مقدار·실행할 수 없다.
기술적으로 필요한 اجرا_فرمان 환경을 추가하거나 Codex를 이식하는 경로는 있으나,
다운로드 فرمان 하나를 추가하는 작업으로 해결되지 않는다. JDK/JRE 기능 확장만으로도 해결되지 않는다.

## 확인한 근거

| ورودی_مقدار | 현재 소스에서 확인한 وضعیت_مقدار | 직접 실행을 위한 작업 |
|---|---|---|
| اجرا_فرمان پرونده | `دستگاه/کاربر.c`: AArch64 ET_EXEC만, PT_INTERP/PT_DYNAMIC/PT_TLS رد_کردن_مقدار, 업로드 اجرا_فرمان 버퍼 16384바이트 | هدف 바이너리에 맞는 ELF 적재·재배치·اجرا_فرمان آماده_سازی, حافظه_داده_ها/پرونده 제한 تمدید_مقدار |
| Linux ABI | `دستگاه/리눅스호환.inc`: read/write/openat/brk 등 제한된 번호만 فرآیند_مقدار_ورودی, 나머지는 ENOSYS | libc/런타임에 필요한 시스템 호출을 추가하거나 بومی ABI용 런타임 이식 |
| 프로세스·스레드 | 일반 fork/clone/execve, pthread/futex, 시그널, mmap, poll/epoll 계열이 미완성 | 비동기 I/O·스레드·فرزند_مقدار فرمان اجرا_فرمان·خروج_برنامه/لغو_عملیات 기능 |
| پرونده | `مبداء/حافظه_فایل.java`: RAM پرونده 64개, 파일당 16 KiB, 비영속 | 큰 اجرا_فرمان پرونده·프로젝트·تنظیمات·세션을 위한 영속 VFS, پرونده مجوز_مقدار·مسیر·디렉터리 تمدید_مقدار |
| 네트워크 | lwIP TCP/UDP는 있으나 `شبکه_پشته/lwipopts.h`의 LWIP_DNS=0, 일반 HTTPS 클라이언트 없음 | DNS, TLS 인증서 ارزیابی_کردن·신뢰 مخزن_جذر·정확한 시각, HTTPS/스트리밍 |
| پایانه·ابزارها | بومی 셸과 GUI 터미널은 있지만 표준 PTY·일반 프로세스 작업 کنترل_مقدار 없음 | محاوره_ای CLI용 پایانه 기능, واسط/پرونده 검색/ساخت_سیستم ابزارها اتصال |
| اجرا_فرمان مجوز_مقدار | EL0 보호는 있으나 Codex의 Linux 샌드박스와 같은 정책 집행 환경 없음 | پرونده·네트워크·فرمان مجوز_مقدار 정책과 승인 기능; بومی 커널에 맞는 격리 구현 |

여기서 ELF의 PT_TLS는 스레드별 ذخیره_مقدار 공간이다. HTTPS의 TLS رمز_عبور_مقدار 통신과 서로 다른 기능이다.
ELF پرونده 형식을 읽을 수 있다는 사실만으로 Linux اجرا_فرمان 환경을 제공하는 것은 아니다.
SSH/VNC를 위한 رمز_عبور_مقدار 라이브러리를 넣은 상태도 HTTPS 구현 완료를 의미하지 않는다.

호스트의 `/home/user/.local/bin/codex`도 확인했다. 이것은 x86-64 ELF ET_DYN이며 약 209 MiB다.
해당 파일을 ARM64 게스트로 복사하여 실행할 수 없다. 이 크기를 ARM64 배포 파일의 크기로
해석하지 않는다. 공식 ARM64 빌드의 واقعی_داده_ها اندازه·의존성은 설치할 버전으로 추가 검사해야 한다.

## 가능한 구현 مسیر

1. **بومی 커널에 공식 CLI 직접 이식**
   영속 ذخیره_مقدار/VFS와 کاربر حافظه_داده_ها, 프로세스·스레드·I/O, libc/런타임, DNS/HTTPS,
   پایانه·مجوز_مقدار 체계를 갖춘다. 이후 هدف 버전의 의존성을 조사하여 크로스 ساخت_سیستم·이식한다.
   Linux 커널을 반드시 탑재할 필요는 없지만, 공식 Linux 바이너리를 그대로 쓸 경우
   그 바이너리가 사용하는 Linux ABI까지 호환해야 한다. 큰 سیستم_عامل 개발 과제다.

2. **외부 میزبان Codex와 بومی هسته_مقدار اتصال — 첫 구현으로 권장**
   Linux PC에서 공식 CLI 또는 app-server를 실행하고 jkoros에는 전용 کاربر فرمان/화면을 만든다.
   호스트의 인증된 연결과 게스트 پرونده خواندن·수정·업로드·فرمان اجرا_فرمان 어댑터가 필요하다.
   기존 SSH/TCP 경로를 활용할 수 있으나, پرونده 동기화나 Codex 전용 어댑터는 현재 구현되어 있지 않다.
   호스트에서 수행한 빌드와 게스트에서 수행한 اجرا_فرمان 결과를 명확히 구분한다.
   이 구성은 بومی 커널을 유지하지만, 공식 CLI 자체는 외부 호스트에서 실행된다.

3. **بومی API 클라이언트 제작**
   بومی ABI의 C 또는 지원되는 Java 부분집합으로 محاوره_ای_جلسه UI와 پرونده/فرمان ابزارها 호출 루프를 만든다.
   외부 중계기를 쓰지 않는다면 DNS/ارزیابی_کردن 가능한 TLS/HTTPS와 인증 داده_ها 저장을 먼저 구현해야 한다.
   이는 OpenAI API를 이용하는 별도 에이전트이며 공식 Codex CLI 전체의 이식으로 표시하지 않는다.

4. **별도 ARM64 Linux 실행판에서 نصب_مقدار**
   `../rpi4`는 Linux와 musl 기반이므로 일반 Linux نصب_مقدار 경로를 검토할 수 있다.
   사용할 Codex 버전의 ARM64·musl 호환성, 의존성, 커널의 샌드박스 지원을 واقعی_داده_ها 검증해야 한다.
   이번 검토에서 نصب_مقدار 성공을 확인하지 않았다. 이 결과를 بومی Java 커널의 지원으로 표시하지 않는다.

## 단계별 완료 نمایش_دادن_جذر

- 직접 이식: `--version` اجرا_2 → 인증/HTTPS → پرونده خواندن·수정 → فرزند_مقدار فرمان اجرا_فرمان →
  محاوره_ای 입력/스트리밍 → مجوز_مقدار 제한·لغو_عملیات → 재부팅 후 تنظیمات/세션 보존을 각각 واقعی_داده_ها 게스트에서 확인한다.
- میزبان اتصال: 게스트에서 요청 입력 → میزبان Codex فرآیند_مقدار_ورودی → 게스트 پرونده تغییر_مقدار تأیید_صحت →
  게스트 javac/cc اجرا_فرمان → سنجش 표시를 처음부터 끝까지 검증한다.
- COSL 상업 조건을 유지하려면 새로 도입하는 런타임/통신 라이브러리의 라이선스와
  Codex 배포 버전의 제3자 고지를 검토한다. 외부 구성요소를 일괄 COSL로 재라이선스하지 않는다.

## 공식 문서

- [Codex CLI نصب_مقدار 및 کنش](https://learn.chatgpt.com/docs/codex/cli): 표준 Linux/macOS 독립 نصب_مقدار 경로와 프로젝트 پرونده·فرمان 작업.
- [인증](https://learn.chatgpt.com/docs/auth): ChatGPT/API 인증, 헤드리스 장치의 `codex login --device-auth`, HTTPS 인증서 تنظیمات.
- [샌드박스](https://learn.chatgpt.com/docs/sandboxing): 운영체제별 집행 روش_حالت, Linux의 bubblewrap 및 کاربر 네임스페이스 요구 사항.
- [공개 구성요소](https://learn.chatgpt.com/docs/open-source): CLI/SDK/app-server의 공개 منبع_درخت 위치와 비공개 구성요소 مرزبند_مقدار.

공식 문서에는 jkoros를 پشتیبان_مقدار 대상으로 명시한 내용이 없다. 위 구현 مسیر·개발 순서는
현재 소스와 요구 기능을 대조한 기술적 판단이다.
