# 内置 ARM64 커널의 执行命令 层值·프로세스 显示值·QEMU 外部值 通信

2026-10-04 审查状态. 대상은 `jkoros/platforms/rpi4-native`의 内置 Java 커널이다.
`platforms/rpi4`의 Linux/OpenJDK 판이나 `os`의 기존 x86 판에 이 결과를 적용하지 않는다.

## 执行命令 层值

| 目标值 | 执行命令 位置 | 当前项目 实现 |
|---|---|---|
| 命令壳, `sh` 脚本值, `ps`, `top`, 文件 내장 命令 | EL1 内核值 | Java AOT 内核值 함수로 调用 |
| 终端 창과 命令壳 状态值 | 内核值 | 最大值 4개의 상태를 保留值·복원; 독립 命令壳 프로세스가 아님 |
| `java`, `javac` | EL0 用户 区域值 | `java-tools.elf`를 적재하고 별도 用户 操作数栈·페이지 권한으로 执行命令 |
| `java CLASS`, `java -jar`의 程序 | EL0의 内置 JVM 내부 | 字节码 执行命令. 전체 OpenJDK가 아님 |
| `jaot` 结果 ELF | EL0 | 지원되는 부분집합을 ARM64 코드로 컴파일한 之后状态 ELF로 执行命令 |
| `python`, `vi`, `cc`, 用户 ELF | EL0 | 用户 执行命令 文件 적재 路径 使用值 |
| 文件·套接字值·그래픽 시스템 调用 | EL1 | EL0에서 SVC로 들어와 처리한 后端值 用户 프로그램으로 복귀 |

근거:

- `源代码/命令解释器.java`: `工具条目()` 및 `java`/`javac` 命令 分支.
- `计算机/用户.c`: `运行程序()`의 ELF 적재, 페이지 权限值 设置, PID 배정, `用户进入()`.
- `启动/条目分值.S`: `user_enter`의 `SP_EL0`, `SPSR_EL1=0x340`, `eret`.
- `源代码/窗口会话.java`: 네 터미널의 命令壳 상태와 用户 세션 保留值·恢复执行执行状态.

QEMU QMP로 CPU 0을 实际数据 정지하여 읽은 权限值 상태는 命令壳 等待状态值 중 `EL1h`, Java 计算结果 중 `EL0t`였다.
이 결과는 소스의 주석이나 输出 문자열만으로 판정한 것이 아니다.

## ps와 top에 기대한 항목이 없는 理由值

`源代码/系统工具.java`의 `显示任务列()`首位操作数 두 명령의 公用值 출력이다.
`1 ... kernel/shell`은 고정된 内核值/命令壳 统计值 행이다. 셸마다 생성한 实际数据 PID가 아니다.
그 다음에는 살아 있는 内核值 협력 작업과 最大值 4개의 EL0 세션을 조회한다.

1. 셸은 독립 用户 프로세스가 아니므로 터미널을 더 열어도 `shell` 행이 각각 생기지 않는다.
2. 같은 터미널의 `java 问候例`首位操作数 끝난 后端值 `ps`를 실행하면 해당 Java 세션은 이미 정리되어 표시되지 않는다.
3. `vi`第二操作数 Swing 프로그램은 다른 터미널로 전환할 때 CPU 上下文值·메모리를 보관한다. 이 상태가 `SUSPENDED`第三操作数.
4. 한 번에 活跃 EL0 프로그램은 하나다. 다른 창의 프로그램을 동시에 돌리는 일반 선점형 프로세스 스케줄러와 `&` 任务 제어는 없다.
5. Java의 任务 가닥은 内置 JVM 내부에서 협력적으로 전환한다. 별도 内核值 스레드/TID가 아니므로 `ps`에 각각 나타나지 않는다.
6. `ps`·`top` 자체도 内核值 내장 명령이므로 별도의 用户 PID가 생성되지 않는다. `top`은 같은 任务 목록과 内存数据 정보를 주기적으로 보여 준다.

`RUN_ms`는 세션이 선택된 동안의 경과 시간이며 시스템 调用 시간도 포함한다.
Linux의 정밀 CPU 使用值 시간이나 CPU 사용률이 아니다. `MAPPED_KiB`도 用户 페이지 매핑량이다.

실제로 확인하는 방법:

```text
cd /example/java
java 窗口例
```

GUI에서 `Ctrl+Shift+T`로 새 터미널을 열거나 `F6`으로 다른 터미널을 선택한 后端值:

```text
ps
top -n 1
```

이번 시험에서 두 명령에 下一项目 用户 행이 나타났다. PID와 시간은 실행마다 달라진다.

```text
PID SLOT STATE MAPPED_KiB RUN_ms AGE_ms COMMAND
1 - RUN - - 25144 kernel/shell
24 0 SUSPENDED 9608 507 3960 java 窗口例
```

`窗口例.class`는 构建映像 构建系统 때 宿主 `javac`로 컴파일되어 소스와 함께 탑재된다.
게스트 `javac 窗口例.java`는 当前项目 支持值 범위를 넘으며 `unsupported throws type` 오류를 낸다.
이 GUI 점검에는 이미 탑재된 클래스를 실행한다.

셸까지 EL0로 옮기고 프로그램을 동시에 실행하려면 用户 命令壳 执行命令 文件, 프로세스별 地址 地址区域·文件 기술자·任务 디렉터리,
프로세스 生成/等待状态值/退出程序, 스케줄러, TTY 输入输出, 内核值 任务·用户 任务 구분을 추가해야 한다.
`ps` 출력에 이름만 추가해서는 用户 权限值 분리나 동시 실행이 구현되지 않는다.

## QEMU에서 외부로 통신하기

宿主 터미널에서 下一项目 중 하나로 실행한다.

```sh
cd /home/user/jkoros/platforms/rpi4-native
make desktop ARGS="--network"
```

屏幕 없이 UART 셸만 사용할 때는 `make network`를 사용한다.
이미 VM이 执行命令 중이면 退出程序 之前值 RAM 자료를 보관한다. 별도 VM을 띄우려면
`make desktop ARGS="--network --port 5903 --network-host 127.0.0.2"`처럼 VNC와 前向值 주소를 구분한다.

게스트 안에서:

```text
ipconfig
ip route show
ping -c 2 10.0.2.2
```

초깃값은 `sl0`, 地址 `10.0.2.15`, 넷마스크 `255.255.255.0`, 网关值 `10.0.2.2`第三操作数.
정상이면 重试值 설정할 필요가 없다. 주소를 바꿔 둔 경우 套接字值/FTP를 닫은 后端值 기본값으로 돌릴 数 있다.

```text
ftpd stop
ipconfig set 10.0.2.15 255.255.255.0 10.0.2.2
```

通信 路径:

```text
게스트 Java/C/Python → SVC → 内核值 lwIP → 辅助值 UART SLIP
    → 宿主 网络桥接.py → QEMU user NAT → 宿主 TCP/IP → LAN/인터넷
```

QEMU `raspi4b`의 GENET Ethernet Controller는 미구현이다.
当前项目 실행기는 일반 PC용 `-device e1000`이나 `virtio-net-pci` 대신 辅助值 UART를 사용한다.
따라서 `-nic user`만 추가하거나 게스트 주소만 바꿔서는 이 通信 경로를 대신할 数 없다.
[QEMU Raspberry Pi 设备 支持值](https://www.qemu.org/docs/master/system/arm/raspi.html)

게스트에서 `127.0.0.1`은 게스트 자신이며, `10.0.2.2`首位操作数 QEMU 호스트에 접근하는 주소다.
그 밖의 实际数据 IPv4 주소로 향하는 TCP/UDP는 호스트의 路径·방화벽·通信 가능 여부에 따른다.
게스트 DNS와 일반 TLS 소켓은 아직 없다. 도메인 名称 대신 数字值 IPv4를 사용해야 한다. 之后值 추가된 GENET·DHCP 및 게스트 SSH·VNC는 [外部值 接通状态 指南](外部连接状态指南.md)를 참고한다.
`ping 10.0.2.2` 성공은 NAT 관문까지의 확인이지 인터넷 통신의 증거는 아니다.
인터넷 ICMP는 QEMU user NAT와 宿主 `ping_group_range` 설정에 영향받으므로,
外部值 ping 실패만으로 TCP/UDP 통신까지 불가능하다고 판단하지 않는다.
[QEMU NAT 및 ICMP 说明](https://www.qemu.org/docs/master/system/devices/net.html)

## 实际数据 TCP/UDP 왕복 用例

VM을 실행한 상태에서 호스트의 다른 터미널에서:

```sh
cd /home/user/jkoros/platforms/rpi4-native
python3 工具集/回显示例服务器.py --tcp-port 9000 --udp-port 9001
```

게스트 안에서:

```text
cd /example/java
java 网络例 9000 9001
cd /example/python
python 网络例.py 9001
```

Java 예제는 TCP와 UDP, Python 예제는 UDP를 宿主 응답기로 보내고 实际数据 받은 자료를 비교한다.
Java 예제의 클래스는 이미 탑재되어 있다. 이 예제의 接收值 제한은 700ms이므로 느린 호스트에서는
用例 자체의 时间值 제한을 조정해야 할 数 있다.

## 宿主 또는 다른 PC에서 게스트로 접속하기

硬件端口 전달을 执行命令 시 명시한다.

```sh
make desktop ARGS="--network --forward tcp:18080:8080 --forward udp:19001:9001"
```

- 宿主 `127.0.0.1:18080/TCP` → 게스트 `10.0.2.15:8080/TCP`.
- 宿主 `127.0.0.1:19001/UDP` → 게스트 `10.0.2.15:9001/UDP`.
- 게스트 프로그램이 그 포트에서 실제로 수신해야 한다. 前向值 옵션이 서버를 시작하지는 않는다.
- `ftpd start`는 별도로 게스트 FTP를 시작한다. 默认值 宿主 控制值 포트는 2121, 수동 数据 포트는 50000~50007이다.

默认值 `--network-host 127.0.0.1`은 루프백에만 연결한다. 之后值 추가한 外部值 接通状态 기능에서는
`--network-host 0.0.0.0` 또는 宿主 LAN 주소를 명시하면 다른 PC의 직접 접속도 허용한다.
[게스트 SSH·VNC 执行命令 指南](外部连接状态指南.md)를 참고한다.
루프백 연결을 유지하면서 호스트의 SSH 서버를 이용할 경우 다른 PC에서 다음처럼 TCP 터널을 만든다.
`192.168.0.10`은 QEMU를 실행하는 호스트의 实际数据 存取条目 가능한 IP로 바꾼다.

```sh
ssh -N -L 18080:127.0.0.1:18080 user@192.168.0.10
```

다른 PC의 클라이언트는 이제 自身引用 `127.0.0.1:18080`에 연결한다.
이것이 SSH를 거쳐 호스트의 QEMU 前向值 포트와 게스트 8080에 연결된다.
SSH의 `-L`은 TCP 전용이다. UDP를 LAN에서 직접 받거나 게스트를 LAN의 독립 IP로 쓰려면
追加条目 UDP 中继值 또는 TAP/브리지 백엔드 연결이 필요하며 当前项目 执行命令 옵션만으로는 제공하지 않는다.
FTP는 控制值 포트뿐 아니라 수동 数据 硬件端口 전체도 전달해야 한다.

QEMU를 Ubuntu 가상머신 안에서 실행하는 경우 위의 '宿主 IP'는 그 Ubuntu의 주소다.
Ubuntu를 실행하는 바깥 가상화 프로그램도 해당 IP/SSH 포트에 存取条目 가능한 네트워크 구성이 필요하다.

## 审查状态 재현과 验证 裁剪

```sh
make test-layers
```

- QMP CPU 0 레지스터: 命令壳 `EL1h`, Java 计算结果 `EL0t`.
- 종료된 Java 프로그램의 `ps` 条目值 移除条目.
- Java GUI의 다른 终端 切换模式 之后状态 별도 PID 및 `SUSPENDED` 상태를 `ps`와 `top`에서 验证.
- 网关值 ICMP 왕복, FTP 类值 업로드.
- 독립 宿主 상대와 TCP/UDP 발신, 명시적 硬件端口 전달을 통한 TCP/UDP 接收值 및 数据 비교.
- 退出程序 시 이번 점검이 만든 QEMU만 清洁构建.

결과는 [보고서](build/verification/execution-network-review/report.json)와
[串行值 日志值](build/verification/execution-network-review/serial.log)에 저장한다.
보고서에 사용한 内核值 SHA-256과 원시 QMP 레지스터를 남긴다.
최초 시도에서는 지원하지 않는 GUI 소스의 게스트 재컴파일 단계가 실패했고,
`initial-attempt-report.json`/`initial-attempt-serial.log`에 기록을 보관했다.
탑재된 GUI 类值 사용으로 审查状态 절차를 수정한 之后状态 顶端值 항목은 构建全部 통과했다.

이번 实际数据 通信 검증의 범위는 **게스트와 QEMU 밖의 독립 宿主 程序 分隔条**第三操作数.
별도 물리 PC, 공인 인터넷 目的地址端点, SSH 터널, 实际数据 Pi 4 Ethernet에서의 송수신은 시험하지 않았다.
内核值 셸을 用户 셸로 이식하거나 일반 프로세스 스케줄러를 추가한 변경은 아니다.
