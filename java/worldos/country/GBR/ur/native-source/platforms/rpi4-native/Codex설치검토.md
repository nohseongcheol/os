# اپنا ARM64 커널의 Codex نصب_کریں_قدر 가능성 검토

검토일: 2026-10-05. 소스와 공식 문서를 대조한 설계 검토이며, 게스트에 Codex를 설치하거나
로그인·모델 호출을 실행한 결과는 아니다. اپنا ARM64 커널과 `../rpi4` Linux 실행판은 구분한다.

현재 اپنا 커널에는 공식 Codex CLI를 그대로 نصب_کریں_قدر·실행할 수 없다.
기술적으로 필요한 نفاذ_کریں_حکم 환경을 추가하거나 Codex를 이식하는 경로는 있으나,
다운로드 حکم 하나를 추가하는 작업으로 해결되지 않는다. JDK/JRE 기능 확장만으로도 해결되지 않는다.

## 확인한 근거

| اندراج_قدر | 현재 소스에서 확인한 حالت_قدر | 직접 실행을 위한 작업 |
|---|---|---|
| نفاذ_کریں_حکم فائل_کا_نام | `مشین/صارف.c`: AArch64 ET_EXEC만, PT_INTERP/PT_DYNAMIC/PT_TLS رد_کریں_قدر, 업로드 نفاذ_کریں_حکم 버퍼 16384바이트 | ہدف 바이너리에 맞는 ELF 적재·재배치·نفاذ_کریں_حکم ابتدا_کریں, میموری_کوائف/فائل_کا_نام 제한 توسیع_قدر |
| Linux ABI | `مشین/리눅스호환.inc`: read/write/openat/brk 등 제한된 번호만 عمل_قدر_اندراج, 나머지는 ENOSYS | libc/런타임에 필요한 시스템 호출을 추가하거나 اپنا ABI용 런타임 이식 |
| 프로세스·스레드 | 일반 fork/clone/execve, pthread/futex, 시그널, mmap, poll/epoll 계열이 미완성 | 비동기 I/O·스레드·بچہ_قدر حکم نفاذ_کریں_حکم·خروج_ایپ/منسوخ_عملیہ 기능 |
| فائل_کا_نام | `ماخذ_فائل/میموری_فائلیں.java`: RAM فائل_کا_نام 64개, 파일당 16 KiB, 비영속 | 큰 نفاذ_کریں_حکم فائل_کا_نام·프로젝트·ترتیبات·세션을 위한 영속 VFS, فائل_کا_نام اجازت_قدر·راستہ_2·디렉터리 توسیع_قدر |
| 네트워크 | lwIP TCP/UDP는 있으나 `نیٹ_ورک_اسٹیک/lwipopts.h`의 LWIP_DNS=0, 일반 HTTPS 클라이언트 없음 | DNS, TLS 인증서 جواز_دہی_کریں·신뢰 저장소·정확한 시각, HTTPS/스트리밍 |
| حکم_کی_تشریح_کرنے_والا·ٹولز | اپنا 셸과 GUI 터미널은 있지만 표준 PTY·일반 프로세스 작업 کنٹرول_قدر 없음 | متعامل CLI용 حکم_کی_تشریح_کرنے_والا 기능, شیل/فائل_کا_نام 검색/بلڈ_نظام ٹولز متصل_ہوں |
| نفاذ_کریں_حکم اجازت_قدر | EL0 보호는 있으나 Codex의 Linux 샌드박스와 같은 정책 집행 환경 없음 | فائل_کا_نام·네트워크·حکم اجازت_قدر 정책과 승인 기능; اپنا 커널에 맞는 격리 구현 |

여기서 ELF의 PT_TLS는 스레드별 ذخیرہ_کریں_قدر 공간이다. HTTPS의 TLS پاس_ورڈ_قدر 통신과 서로 다른 기능이다.
ELF فائل_کا_نام 형식을 읽을 수 있다는 사실만으로 Linux نفاذ_کریں_حکم 환경을 제공하는 것은 아니다.
SSH/VNC를 위한 پاس_ورڈ_قدر 라이브러리를 넣은 상태도 HTTPS 구현 완료를 의미하지 않는다.

호스트의 `/home/user/.local/bin/codex`도 확인했다. 이것은 x86-64 ELF ET_DYN이며 약 209 MiB다.
해당 파일을 ARM64 게스트로 복사하여 실행할 수 없다. 이 크기를 ARM64 배포 파일의 크기로
해석하지 않는다. 공식 ARM64 빌드의 اصل_کوائف حجم·의존성은 설치할 버전으로 추가 검사해야 한다.

## 가능한 구현 راستہ_2

1. **اپنا 커널에 공식 CLI 직접 이식**
   영속 ذخیرہ_کریں_قدر/VFS와 صارف میموری_کوائف, 프로세스·스레드·I/O, libc/런타임, DNS/HTTPS,
   حکم_کی_تشریح_کرنے_والا·اجازت_قدر 체계를 갖춘다. 이후 ہدف 버전의 의존성을 조사하여 크로스 بلڈ_نظام·이식한다.
   Linux 커널을 반드시 탑재할 필요는 없지만, 공식 Linux 바이너리를 그대로 쓸 경우
   그 바이너리가 사용하는 Linux ABI까지 호환해야 한다. 큰 آپریٹنگ_سسٹم 개발 과제다.

2. **외부 میزبان Codex와 اپنا کرنیل_قدر متصل_ہوں — 첫 구현으로 권장**
   Linux PC에서 공식 CLI 또는 app-server를 실행하고 jkoros에는 전용 صارف حکم/화면을 만든다.
   호스트의 인증된 연결과 게스트 فائل_کا_نام پڑھیں·수정·업로드·حکم نفاذ_کریں_حکم 어댑터가 필요하다.
   기존 SSH/TCP 경로를 활용할 수 있으나, فائل_کا_نام 동기화나 Codex 전용 어댑터는 현재 구현되어 있지 않다.
   호스트에서 수행한 빌드와 게스트에서 수행한 نفاذ_کریں_حکم 결과를 명확히 구분한다.
   이 구성은 اپنا 커널을 유지하지만, 공식 CLI 자체는 외부 호스트에서 실행된다.

3. **اپنا API 클라이언트 제작**
   اپنا ABI의 C 또는 지원되는 Java 부분집합으로 متعامل_سیشن UI와 فائل_کا_نام/حکم ٹولز 호출 루프를 만든다.
   외부 중계기를 쓰지 않는다면 DNS/جواز_دہی_کریں 가능한 TLS/HTTPS와 인증 کوائف 저장을 먼저 구현해야 한다.
   이는 OpenAI API를 이용하는 별도 에이전트이며 공식 Codex CLI 전체의 이식으로 표시하지 않는다.

4. **별도 ARM64 Linux 실행판에서 نصب_کریں_قدر**
   `../rpi4`는 Linux와 musl 기반이므로 일반 Linux نصب_کریں_قدر 경로를 검토할 수 있다.
   사용할 Codex 버전의 ARM64·musl 호환성, 의존성, 커널의 샌드박스 지원을 اصل_کوائف 검증해야 한다.
   이번 검토에서 نصب_کریں_قدر 성공을 확인하지 않았다. 이 결과를 اپنا Java 커널의 지원으로 표시하지 않는다.

## 단계별 완료 عکس_ڈالنا_روٹ

- 직접 이식: `--version` چلائیں → 인증/HTTPS → فائل_کا_نام پڑھیں·수정 → بچہ_قدر حکم نفاذ_کریں_حکم →
  متعامل 입력/스트리밍 → اجازت_قدر 제한·منسوخ_عملیہ → 재부팅 후 ترتیبات/세션 보존을 각각 اصل_کوائف 게스트에서 확인한다.
- میزبان متصل_ہوں: 게스트에서 요청 입력 → میزبان Codex عمل_قدر_اندراج → 게스트 فائل_کا_نام تبدیل_کریں_قدر تصدیق_کریں →
  게스트 javac/cc نفاذ_کریں_حکم → پیمائش 표시를 처음부터 끝까지 검증한다.
- COSL 상업 조건을 유지하려면 새로 도입하는 런타임/통신 라이브러리의 라이선스와
  Codex 배포 버전의 제3자 고지를 검토한다. 외부 구성요소를 일괄 COSL로 재라이선스하지 않는다.

현재 소스와 요구 기능을 대조한 기술적 판단이다.
