# 자체 ARM64 커널의 Codex ସଂସ୍ଥାପନ_ମୂଲ୍ୟ 가능성 검토

검토일: 2026-10-05. 소스와 공식 문서를 대조한 설계 검토이며, 게스트에 Codex를 설치하거나
로그인·모델 호출을 실행한 결과는 아니다. 자체 ARM64 커널과 `../rpi4` Linux 실행판은 구분한다.

현재 자체 커널에는 공식 Codex CLI를 그대로 ସଂସ୍ଥାପନ_ମୂଲ୍ୟ·실행할 수 없다.
기술적으로 필요한 ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ 환경을 추가하거나 Codex를 이식하는 경로는 있으나,
다운로드 ନିର୍ଦ୍ଦେଶ 하나를 추가하는 작업으로 해결되지 않는다. JDK/JRE 기능 확장만으로도 해결되지 않는다.

## 확인한 근거

| ଏଣ୍ଟ୍ରି_ମୂଲ୍ୟ | 현재 소스에서 확인한 ସ୍ଥିତି_ମୂଲ୍ୟ_e10195a1 | 직접 실행을 위한 작업 |
|---|---|---|
| ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ ଫାଇଲ | `ମେସିନ୍/ଉପଭୋକ୍ତା.c`: AArch64 ET_EXEC만, PT_INTERP/PT_DYNAMIC/PT_TLS ପ୍ରତ୍ୟାକ୍ଷାନ_ମୂଲ୍ୟ, 업로드 ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ 버퍼 16384바이트 | ଲକ୍ଷ୍ୟସ୍ଥଳ 바이너리에 맞는 ELF 적재·재배치·ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ ପ୍ରାରମ୍ଭିକରଣ, ମୋମରୀ_ଡାଟା/ଫାଇଲ 제한 ଏକ୍ସଟେନସନ୍_ମୂଲ୍ୟ |
| Linux ABI | `ମେସିନ୍/리눅스호환.inc`: read/write/openat/brk 등 제한된 번호만 ପ୍ରୋସେସ୍_ମୂଲ୍ୟ_ଏଣ୍ଟ୍ରି, 나머지는 ENOSYS | libc/런타임에 필요한 시스템 호출을 추가하거나 자체 ABI용 런타임 이식 |
| 프로세스·스레드 | 일반 fork/clone/execve, pthread/futex, 시그널, mmap, poll/epoll 계열이 미완성 | 비동기 I/O·스레드·ଶିଶୁ_ମୂଲ୍ୟ ନିର୍ଦ୍ଦେଶ ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ·ପ୍ରସ୍ଥାନ_ଅନୁପ୍ରୟୋଗ/ବାତିଲ୍_ସଂଚାଳନ 기능 |
| ଫାଇଲ | `ଉତ୍ସ/ମୋମରୀ_ଫାଇଲ୍_ଗୁଡିକ.java`: RAM ଫାଇଲ 64개, 파일당 16 KiB, 비영속 | 큰 ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ ଫାଇଲ·프로젝트·ବିନ୍ଯାସ·세션을 위한 영속 VFS, ଫାଇଲ ଅନୁମତି_ମୂଲ୍ୟ·ପଥ·디렉터리 ଏକ୍ସଟେନସନ୍_ମୂଲ୍ୟ |
| 네트워크 | lwIP TCP/UDP는 있으나 `ନେଟ୍_ୱାର୍କ୍_ଗଦା/lwipopts.h`의 LWIP_DNS=0, 일반 HTTPS 클라이언트 없음 | DNS, TLS 인증서 ବୈଧକରଣ·신뢰 저장소·정확한 시각, HTTPS/스트리밍 |
| ଟର୍ମିନାଲ·ଉପକରଣସମୂହ | 자체 셸과 GUI 터미널은 있지만 표준 PTY·일반 프로세스 작업 ନିୟନ୍ତ୍ରଣ_ମୂଲ୍ୟ 없음 | ଆଦାନ_ପ୍ରଦାନ_ଯୋଗ୍ୟ CLI용 ଟର୍ମିନାଲ 기능, ଖୋଳ/ଫାଇଲ 검색/ବିଲ୍ଡ୍_ସିଷ୍ଟମ ଉପକରଣସମୂହ ସଂଯୋଗ_କରନ୍ତୁ |
| ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ ଅନୁମତି_ମୂଲ୍ୟ | EL0 보호는 있으나 Codex의 Linux 샌드박스와 같은 정책 집행 환경 없음 | ଫାଇଲ·네트워크·ନିର୍ଦ୍ଦେଶ ଅନୁମତି_ମୂଲ୍ୟ 정책과 승인 기능; 자체 커널에 맞는 격리 구현 |

여기서 ELF의 PT_TLS는 스레드별 ସଞ୍ଚୟ_କରିବା_ମୂଲ୍ୟ 공간이다. HTTPS의 TLS ପାସ୍_ୱାର୍ଡ୍_ମୂଲ୍ୟ 통신과 서로 다른 기능이다.
ELF ଫାଇଲ 형식을 읽을 수 있다는 사실만으로 Linux ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ 환경을 제공하는 것은 아니다.
SSH/VNC를 위한 ପାସ୍_ୱାର୍ଡ୍_ମୂଲ୍ୟ 라이브러리를 넣은 상태도 HTTPS 구현 완료를 의미하지 않는다.

호스트의 `/home/user/.local/bin/codex`도 확인했다. 이것은 x86-64 ELF ET_DYN이며 약 209 MiB다.
해당 파일을 ARM64 게스트로 복사하여 실행할 수 없다. 이 크기를 ARM64 배포 파일의 크기로
해석하지 않는다. 공식 ARM64 빌드의 ପ୍ରକୃତ_ଡାଟା ଆକାର·의존성은 설치할 버전으로 추가 검사해야 한다.

## 가능한 구현 ପଥ

1. **자체 커널에 공식 CLI 직접 이식**
   영속 ସଞ୍ଚୟ_କରିବା_ମୂଲ୍ୟ/VFS와 ଉପଭୋକ୍ତା ମୋମରୀ_ଡାଟା, 프로세스·스레드·I/O, libc/런타임, DNS/HTTPS,
   ଟର୍ମିନାଲ·ଅନୁମତି_ମୂଲ୍ୟ 체계를 갖춘다. 이후 ଲକ୍ଷ୍ୟସ୍ଥଳ 버전의 의존성을 조사하여 크로스 ବିଲ୍ଡ୍_ସିଷ୍ଟମ·이식한다.
   Linux 커널을 반드시 탑재할 필요는 없지만, 공식 Linux 바이너리를 그대로 쓸 경우
   그 바이너리가 사용하는 Linux ABI까지 호환해야 한다. 큰 ଅପରେଟିଂ_ସିଷ୍ଟମ 개발 과제다.

2. **외부 ଆୟୋଜକ Codex와 자체 କେନ୍ଦ୍ରିକ_ମୂଲ୍ୟ ସଂଯୋଗ_କରନ୍ତୁ — 첫 구현으로 권장**
   Linux PC에서 공식 CLI 또는 app-server를 실행하고 jkoros에는 전용 ଉପଭୋକ୍ତା ନିର୍ଦ୍ଦେଶ/화면을 만든다.
   호스트의 인증된 연결과 게스트 ଫାଇଲ ପଢନ୍ତୁ·수정·업로드·ନିର୍ଦ୍ଦେଶ ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ 어댑터가 필요하다.
   기존 SSH/TCP 경로를 활용할 수 있으나, ଫାଇଲ 동기화나 Codex 전용 어댑터는 현재 구현되어 있지 않다.
   호스트에서 수행한 빌드와 게스트에서 수행한 ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ 결과를 명확히 구분한다.
   이 구성은 자체 커널을 유지하지만, 공식 CLI 자체는 외부 호스트에서 실행된다.

3. **자체 API 클라이언트 제작**
   자체 ABI의 C 또는 지원되는 Java 부분집합으로 ଆଦାନ_ପ୍ରଦାନ_ଯୋଗ୍ୟ_ଅଧିବେଶନ UI와 ଫାଇଲ/ନିର୍ଦ୍ଦେଶ ଉପକରଣସମୂହ 호출 루프를 만든다.
   외부 중계기를 쓰지 않는다면 DNS/ବୈଧକରଣ 가능한 TLS/HTTPS와 인증 ଡାଟା 저장을 먼저 구현해야 한다.
   이는 OpenAI API를 이용하는 별도 에이전트이며 공식 Codex CLI 전체의 이식으로 표시하지 않는다.

4. **별도 ARM64 Linux 실행판에서 ସଂସ୍ଥାପନ_ମୂଲ୍ୟ**
   `../rpi4`는 Linux와 musl 기반이므로 일반 Linux ସଂସ୍ଥାପନ_ମୂଲ୍ୟ 경로를 검토할 수 있다.
   사용할 Codex 버전의 ARM64·musl 호환성, 의존성, 커널의 샌드박스 지원을 ପ୍ରକୃତ_ଡାଟା 검증해야 한다.
   이번 검토에서 ସଂସ୍ଥାପନ_ମୂଲ୍ୟ 성공을 확인하지 않았다. 이 결과를 자체 Java 커널의 지원으로 표시하지 않는다.

## 단계별 완료 ପ୍ରୋଜେକ୍ଟ୍_ରୁଟ୍

- 직접 이식: `--version` ଚଳାନ୍ତୁ → 인증/HTTPS → ଫାଇଲ ପଢନ୍ତୁ·수정 → ଶିଶୁ_ମୂଲ୍ୟ ନିର୍ଦ୍ଦେଶ ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ →
  ଆଦାନ_ପ୍ରଦାନ_ଯୋଗ୍ୟ 입력/스트리밍 → ଅନୁମତି_ମୂଲ୍ୟ 제한·ବାତିଲ୍_ସଂଚାଳନ → 재부팅 후 ବିନ୍ଯାସ/세션 보존을 각각 ପ୍ରକୃତ_ଡାଟା 게스트에서 확인한다.
- ଆୟୋଜକ ସଂଯୋଗ_କରନ୍ତୁ: 게스트에서 요청 입력 → ଆୟୋଜକ Codex ପ୍ରୋସେସ୍_ମୂଲ୍ୟ_ଏଣ୍ଟ୍ରି → 게스트 ଫାଇଲ ପରିବର୍ତ୍ତନ_ମୂଲ୍ୟ ଯାଞ୍ଚ୍_କରିବା →
  게스트 javac/cc ନିର୍ବାହ_କରିବା_ନିର୍ଦ୍ଦେଶ → ମାପ 표시를 처음부터 끝까지 검증한다.
- COSL 상업 조건을 유지하려면 새로 도입하는 런타임/통신 라이브러리의 라이선스와
  Codex 배포 버전의 제3자 고지를 검토한다. 외부 구성요소를 일괄 COSL로 재라이선스하지 않는다.
