# 자체 ARM64 커널의 Codex орнату_мән 가능성 검토

검토일: 2026-10-05. 소스와 공식 문서를 대조한 설계 검토이며, 게스트에 Codex를 설치하거나
로그인·모델 호출을 실행한 결과는 아니다. 자체 ARM64 커널과 `../rpi4` Linux 실행판은 구분한다.

ток_элемент 자체 커널에는 공식 Codex CLI를 그대로 орнату_мән·실행할 수 없다.
기술적으로 필요한 орындау_пәрмен 환경을 추가하거나 Codex를 이식하는 경로는 있으나,
다운로드 Команда 하나를 추가하는 작업으로 해결되지 않는다. JDK/JRE 기능 확장만으로도 해결되지 않는다.

## 확인한 근거

| енгізу_мән | ток_элемент 소스에서 확인한 күй_мән | 직접 실행을 위한 작업 |
|---|---|---|
| орындау_пәрмен Файл | `компьютер/пайдаланушы.c`: AArch64 ET_EXEC만, PT_INTERP/PT_DYNAMIC/PT_TLS қабылдамау_мән, 업로드 орындау_пәрмен 버퍼 16384바이트 | мақсатты_мән 바이너리에 맞는 ELF 적재·재배치·орындау_пәрмен баптандыру, Жад_деректер/Файл 제한 кеңейтім_мән |
| Linux ABI | `компьютер/리눅스호환.inc`: read/write/openat/brk 등 제한된 번호만 Процесс_мән_енгізу, 나머지는 ENOSYS | libc/런타임에 필요한 시스템 호출을 추가하거나 자체 ABI용 런타임 이식 |
| 프로세스·스레드 | 일반 fork/clone/execve, pthread/futex, 시그널, mmap, poll/epoll 계열이 미완성 | 비동기 I/O·스레드·еншілес_элемент_мән Команда орындау_пәрмен·Шығу_бағдарлама/бас_тарту_ота 기능 |
| Файл | `Неден/Жад_Файлдар.java`: RAM Файл 64개, 파일당 16 KiB, 비영속 | 큰 орындау_пәрмен Файл·프로젝트·Баптаулар·세션을 위한 영속 VFS, Файл рұқсат_мән·Жол_2·디렉터리 кеңейтім_мән |
| 네트워크 | lwIP TCP/UDP는 있으나 `желі_Бума/lwipopts.h`의 LWIP_DNS=0, 일반 HTTPS 클라이언트 없음 | DNS, TLS 인증서 тексеру_5fb2b747·신뢰 репозиторий_түбір·정확한 시각, HTTPS/스트리밍 |
| Терминал·Құралдар | 자체 셸과 GUI 터미널은 있지만 표준 PTY·일반 프로세스 작업 Басқару_мән 없음 | көзбе_көз_белсенді CLI용 Терминал 기능, қоршам/Файл 검색/құрастыру_жүйе Құралдар Байланысу |
| орындау_пәрмен рұқсат_мән | EL0 보호는 있으나 Codex의 Linux 샌드박스와 같은 정책 집행 환경 없음 | Файл·네트워크·Команда рұқсат_мән 정책과 승인 기능; 자체 커널에 맞는 격리 구현 |

여기서 ELF의 PT_TLS는 스레드별 сақтау_мән 공간이다. HTTPS의 TLS құпиясөз_мән 통신과 서로 다른 기능이다.
ELF Файл 형식을 읽을 수 있다는 사실만으로 Linux орындау_пәрмен 환경을 제공하는 것은 아니다.
SSH/VNC를 위한 құпиясөз_мән 라이브러리를 넣은 상태도 HTTPS 구현 완료를 의미하지 않는다.

호스트의 `/home/user/.local/bin/codex`도 확인했다. 이것은 x86-64 ELF ET_DYN이며 약 209 MiB다.
해당 파일을 ARM64 게스트로 복사하여 실행할 수 없다. 이 크기를 ARM64 배포 파일의 크기로
해석하지 않는다. 공식 ARM64 빌드의 нақты_деректер Өлшемі·의존성은 설치할 버전으로 қосу_енгізу 검사해야 한다.

## 가능한 구현 Жол_2

1. **자체 커널에 공식 CLI 직접 이식**
   영속 сақтау_мән/VFS와 пайдаланушы Жад_деректер, 프로세스·스레드·I/O, libc/런타임, DNS/HTTPS,
   Терминал·рұқсат_мән 체계를 갖춘다. 이후 мақсатты_мән 버전의 의존성을 조사하여 크로스 құрастыру_жүйе·이식한다.
   Linux 커널을 반드시 탑재할 필요는 없지만, 공식 Linux 바이너리를 그대로 쓸 경우
   그 바이너리가 사용하는 Linux ABI까지 호환해야 한다. 큰 операциялық_жүйе 개발 과제다.

2. **сыртқы_мән орналастыру Codex와 자체 ядро_мән Байланысу — 첫 구현으로 권장**
   Linux PC에서 공식 CLI 또는 app-server를 실행하고 jkoros에는 전용 пайдаланушы Команда/화면을 만든다.
   호스트의 인증된 연결과 게스트 Файл Оқу·수정·업로드·Команда орындау_пәрмен 어댑터가 필요하다.
   기존 SSH/TCP 경로를 활용할 수 있으나, Файл 동기화나 Codex 전용 어댑터는 ток_элемент 구현되어 있지 않다.
   호스트에서 수행한 빌드와 게스트에서 수행한 орындау_пәрмен 결과를 명확히 구분한다.
   이 구성은 자체 커널을 유지하지만, 공식 CLI 자체는 сыртқы_мән 호스트에서 실행된다.

3. **자체 API 클라이언트 제작**
   자체 ABI의 C 또는 지원되는 Java 부분집합으로 көзбе_көз_белсенді_сеанс UI와 Файл/Команда Құралдар 호출 루프를 만든다.
   сыртқы_мән 중계기를 쓰지 않는다면 DNS/тексеру_5fb2b747 가능한 TLS/HTTPS와 인증 деректер 저장을 먼저 구현해야 한다.
   이는 OpenAI API를 이용하는 별도 에이전트이며 공식 Codex CLI 전체의 이식으로 표시하지 않는다.

4. **별도 ARM64 Linux 실행판에서 орнату_мән**
   `../rpi4`는 Linux와 musl 기반이므로 일반 Linux орнату_мән 경로를 검토할 수 있다.
   사용할 Codex 버전의 ARM64·musl 호환성, 의존성, 커널의 샌드박스 지원을 нақты_деректер 검증해야 한다.
   이번 검토에서 орнату_мән 성공을 확인하지 않았다. 이 결과를 자체 Java 커널의 지원으로 표시하지 않는다.

## 단계별 완료 жоба_түбір

- 직접 이식: `--version` Орындау_2 → 인증/HTTPS → Файл Оқу·수정 → еншілес_элемент_мән Команда орындау_пәрмен →
  көзбе_көз_белсенді 입력/스트리밍 → рұқсат_мән 제한·бас_тарту_ота → 재부팅 후 Баптаулар/세션 보존을 각각 нақты_деректер 게스트에서 확인한다.
- орналастыру Байланысу: 게스트에서 요청 입력 → орналастыру Codex Процесс_мән_енгізу → 게스트 Файл өзгерту_мән тексеру →
  게스트 javac/cc орындау_пәрмен → НӘТИЖЕ 표시를 처음부터 끝까지 검증한다.
- COSL 상업 조건을 유지하려면 새로 도입하는 런타임/통신 라이브러리의 라이선스와
  Codex 배포 버전의 제3자 고지를 검토한다. сыртқы_мән 구성요소를 일괄 COSL로 재라이선스하지 않는다.

ток_элемент 소스와 요구 기능을 대조한 기술적 판단이다.
