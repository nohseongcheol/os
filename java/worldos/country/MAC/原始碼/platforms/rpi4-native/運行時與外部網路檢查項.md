# 內建 ARM64 커널의 執行命令 層值·프로세스 顯示值·QEMU 外部值 通信

2026-10-04 審查狀態. 대상은 `jkoros/platforms/rpi4-native`의 內建 Java 커널이다.
`platforms/rpi4`의 Linux/OpenJDK 판이나 `os`의 기존 x86 판에 이 결과를 적용하지 않는다.

## 執行命令 層值

| 目標值 | 執行命令 位置 | 當前項目 實現 |
|---|---|---|
| 命令殼, `sh` 腳本值, `ps`, `top`, 檔案 내장 命令 | EL1 內核值 | Java AOT 內核值 함수로 調用 |
| 終端 창과 命令殼 狀態值 | 內核值 | 最大值 4개의 상태를 保留值·복원; 독립 命令殼 프로세스가 아님 |
| `java`, `javac` | EL0 使用者 區域值 | `java-tools.elf`를 적재하고 별도 使用者 操作數棧·페이지 권한으로 執行命令 |
| `java CLASS`, `java -jar`의 程式 | EL0의 內建 JVM 내부 | 字節碼 執行命令. 전체 OpenJDK가 아님 |
| `jaot` 結果 ELF | EL0 | 지원되는 부분집합을 ARM64 코드로 컴파일한 之後狀態 ELF로 執行命令 |
| `python`, `vi`, `cc`, 使用者 ELF | EL0 | 使用者 執行命令 檔案 적재 路徑 使用值 |
| 檔案·通訊端值·그래픽 시스템 調用 | EL1 | EL0에서 SVC로 들어와 처리한 後端值 使用者 프로그램으로 복귀 |

근거:

- `原始碼/命令解釋器.java`: `工具條目()` 및 `java`/`javac` 命令 分支.
- `計算機/使用者.c`: `運行程式()`의 ELF 적재, 페이지 權限值 設置, PID 배정, `用戶進入()`.
- `啓動/條目分值.S`: `user_enter`의 `SP_EL0`, `SPSR_EL1=0x340`, `eret`.
- `原始碼/窗口會話.java`: 네 터미널의 命令殼 상태와 使用者 세션 保留值·恢復執行執行狀態.

QEMU QMP로 CPU 0을 實際資料 정지하여 읽은 權限值 상태는 命令殼 等待狀態值 중 `EL1h`, Java 計算結果 중 `EL0t`였다.
이 결과는 소스의 주석이나 輸出 문자열만으로 판정한 것이 아니다.

## ps와 top에 기대한 항목이 없는 理由值

`原始碼/系統工具.java`의 `顯示任務列()`首位操作數 두 명령의 公用值 출력이다.
`1 ... kernel/shell`은 고정된 內核值/命令殼 統計值 행이다. 셸마다 생성한 實際資料 PID가 아니다.
그 다음에는 살아 있는 內核值 협력 작업과 最大值 4개의 EL0 세션을 조회한다.

1. 셸은 독립 使用者 프로세스가 아니므로 터미널을 더 열어도 `shell` 행이 각각 생기지 않는다.
2. 같은 터미널의 `java 問候例`首位操作數 끝난 後端值 `ps`를 실행하면 해당 Java 세션은 이미 정리되어 표시되지 않는다.
3. `vi`第二操作數 Swing 프로그램은 다른 터미널로 전환할 때 CPU 上下文值·메모리를 보관한다. 이 상태가 `SUSPENDED`第三操作數.
4. 한 번에 活躍 EL0 프로그램은 하나다. 다른 창의 프로그램을 동시에 돌리는 일반 선점형 프로세스 스케줄러와 `&` 任務 제어는 없다.
5. Java의 任務 가닥은 內建 JVM 내부에서 협력적으로 전환한다. 별도 內核值 스레드/TID가 아니므로 `ps`에 각각 나타나지 않는다.
6. `ps`·`top` 자체도 內核值 내장 명령이므로 별도의 使用者 PID가 생성되지 않는다. `top`은 같은 任務 목록과 記憶體資料 정보를 주기적으로 보여 준다.

`RUN_ms`는 세션이 선택된 동안의 경과 시간이며 시스템 調用 시간도 포함한다.
Linux의 정밀 CPU 使用值 시간이나 CPU 사용률이 아니다. `MAPPED_KiB`도 使用者 페이지 매핑량이다.

실제로 확인하는 방법:

```text
cd /example/java
java 窗口例
```

GUI에서 `Ctrl+Shift+T`로 새 터미널을 열거나 `F6`으로 다른 터미널을 선택한 後端值:

```text
ps
top -n 1
```

이번 시험에서 두 명령에 下一項目 使用者 행이 나타났다. PID와 시간은 실행마다 달라진다.

```text
PID SLOT STATE MAPPED_KiB RUN_ms AGE_ms COMMAND
1 - RUN - - 25144 kernel/shell
24 0 SUSPENDED 9608 507 3960 java 窗口例
```

`窗口例.class`는 構建映像 構建系統 때 宿主 `javac`로 컴파일되어 소스와 함께 탑재된다.
게스트 `javac 窗口例.java`는 當前項目 支持值 범위를 넘으며 `unsupported throws type` 오류를 낸다.
이 GUI 점검에는 이미 탑재된 클래스를 실행한다.

셸까지 EL0로 옮기고 프로그램을 동시에 실행하려면 使用者 命令殼 執行命令 檔案, 프로세스별 地址 地址區域·檔案 기술자·任務 디렉터리,
프로세스 生成/等待狀態值/退出程式, 스케줄러, TTY 輸入輸出, 內核值 任務·使用者 任務 구분을 추가해야 한다.
`ps` 출력에 이름만 추가해서는 使用者 權限值 분리나 동시 실행이 구현되지 않는다.

## QEMU에서 외부로 통신하기

宿主 터미널에서 下一項目 중 하나로 실행한다.

```sh
cd /home/user/jkoros/platforms/rpi4-native
make desktop ARGS="--network"
```

屏幕 없이 UART 셸만 사용할 때는 `make network`를 사용한다.
이미 VM이 執行命令 중이면 退出程式 之前值 RAM 자료를 보관한다. 별도 VM을 띄우려면
`make desktop ARGS="--network --port 5903 --network-host 127.0.0.2"`처럼 VNC와 前向值 주소를 구분한다.

게스트 안에서:

```text
ipconfig
ip route show
ping -c 2 10.0.2.2
```

초깃값은 `sl0`, 地址 `10.0.2.15`, 넷마스크 `255.255.255.0`, 網關值 `10.0.2.2`第三操作數.
정상이면 重試值 설정할 필요가 없다. 주소를 바꿔 둔 경우 通訊端值/FTP를 닫은 後端值 기본값으로 돌릴 數 있다.

```text
ftpd stop
ipconfig set 10.0.2.15 255.255.255.0 10.0.2.2
```

通信 路徑:

```text
게스트 Java/C/Python → SVC → 內核值 lwIP → 輔助值 UART SLIP
    → 宿主 網路橋接.py → QEMU user NAT → 宿主 TCP/IP → LAN/인터넷
```

QEMU `raspi4b`의 GENET Ethernet Controller는 미구현이다.
當前項目 실행기는 일반 PC용 `-device e1000`이나 `virtio-net-pci` 대신 輔助值 UART를 사용한다.
따라서 `-nic user`만 추가하거나 게스트 주소만 바꿔서는 이 通信 경로를 대신할 數 없다.
[QEMU Raspberry Pi 設備 支持值](https://www.qemu.org/docs/master/system/arm/raspi.html)

게스트에서 `127.0.0.1`은 게스트 자신이며, `10.0.2.2`首位操作數 QEMU 호스트에 접근하는 주소다.
그 밖의 實際資料 IPv4 주소로 향하는 TCP/UDP는 호스트의 路徑·방화벽·通信 가능 여부에 따른다.
게스트 DNS와 일반 TLS 소켓은 아직 없다. 도메인 名稱 대신 數字值 IPv4를 사용해야 한다. 之後值 추가된 GENET·DHCP 및 게스트 SSH·VNC는 [外部值 接通狀態 指南](外部連接狀態指南.md)를 참고한다.
`ping 10.0.2.2` 성공은 NAT 관문까지의 확인이지 인터넷 통신의 증거는 아니다.
인터넷 ICMP는 QEMU user NAT와 宿主 `ping_group_range` 설정에 영향받으므로,
外部值 ping 실패만으로 TCP/UDP 통신까지 불가능하다고 판단하지 않는다.
[QEMU NAT 및 ICMP 說明](https://www.qemu.org/docs/master/system/devices/net.html)

## 實際資料 TCP/UDP 왕복 範例

VM을 실행한 상태에서 호스트의 다른 터미널에서:

```sh
cd /home/user/jkoros/platforms/rpi4-native
python3 工具集/回顯示例服務器.py --tcp-port 9000 --udp-port 9001
```

게스트 안에서:

```text
cd /example/java
java 網路例 9000 9001
cd /example/python
python 網路例.py 9001
```

Java 예제는 TCP와 UDP, Python 예제는 UDP를 宿主 응답기로 보내고 實際資料 받은 자료를 비교한다.
Java 예제의 클래스는 이미 탑재되어 있다. 이 예제의 接收值 제한은 700ms이므로 느린 호스트에서는
範例 자체의 時間值 제한을 조정해야 할 數 있다.

## 宿主 또는 다른 PC에서 게스트로 접속하기

硬件埠 전달을 執行命令 시 명시한다.

```sh
make desktop ARGS="--network --forward tcp:18080:8080 --forward udp:19001:9001"
```

- 宿主 `127.0.0.1:18080/TCP` → 게스트 `10.0.2.15:8080/TCP`.
- 宿主 `127.0.0.1:19001/UDP` → 게스트 `10.0.2.15:9001/UDP`.
- 게스트 프로그램이 그 포트에서 실제로 수신해야 한다. 前向值 옵션이 서버를 시작하지는 않는다.
- `ftpd start`는 별도로 게스트 FTP를 시작한다. 默認值 宿主 控制值 포트는 2121, 수동 資料 포트는 50000~50007이다.

默認值 `--network-host 127.0.0.1`은 루프백에만 연결한다. 之後值 추가한 外部值 接通狀態 기능에서는
`--network-host 0.0.0.0` 또는 宿主 LAN 주소를 명시하면 다른 PC의 직접 접속도 허용한다.
[게스트 SSH·VNC 執行命令 指南](外部連接狀態指南.md)를 참고한다.
루프백 연결을 유지하면서 호스트의 SSH 서버를 이용할 경우 다른 PC에서 다음처럼 TCP 터널을 만든다.
`192.168.0.10`은 QEMU를 실행하는 호스트의 實際資料 存取條目 가능한 IP로 바꾼다.

```sh
ssh -N -L 18080:127.0.0.1:18080 user@192.168.0.10
```

다른 PC의 클라이언트는 이제 自身引用 `127.0.0.1:18080`에 연결한다.
이것이 SSH를 거쳐 호스트의 QEMU 前向值 포트와 게스트 8080에 연결된다.
SSH의 `-L`은 TCP 전용이다. UDP를 LAN에서 직접 받거나 게스트를 LAN의 독립 IP로 쓰려면
追加條目 UDP 中繼值 또는 TAP/브리지 백엔드 연결이 필요하며 當前項目 執行命令 옵션만으로는 제공하지 않는다.
FTP는 控制值 포트뿐 아니라 수동 資料 硬件埠 전체도 전달해야 한다.

QEMU를 Ubuntu 가상머신 안에서 실행하는 경우 위의 '宿主 IP'는 그 Ubuntu의 주소다.
Ubuntu를 실행하는 바깥 가상화 프로그램도 해당 IP/SSH 포트에 存取條目 가능한 네트워크 구성이 필요하다.

## 審查狀態 재현과 驗證 裁剪

```sh
make test-layers
```

- QMP CPU 0 레지스터: 命令殼 `EL1h`, Java 計算結果 `EL0t`.
- 종료된 Java 프로그램의 `ps` 條目值 移除條目.
- Java GUI의 다른 終端 切換模式 之後狀態 별도 PID 및 `SUSPENDED` 상태를 `ps`와 `top`에서 驗證.
- 網關值 ICMP 왕복, FTP 類別值 업로드.
- 독립 宿主 상대와 TCP/UDP 발신, 명시적 硬件埠 전달을 통한 TCP/UDP 接收值 및 資料 비교.
- 退出程式 시 이번 점검이 만든 QEMU만 清潔構建.

결과는 [보고서](build/verification/execution-network-review/report.json)와
[串行值 日誌值](build/verification/execution-network-review/serial.log)에 저장한다.
보고서에 사용한 內核值 SHA-256과 원시 QMP 레지스터를 남긴다.
최초 시도에서는 지원하지 않는 GUI 소스의 게스트 재컴파일 단계가 실패했고,
`initial-attempt-report.json`/`initial-attempt-serial.log`에 기록을 보관했다.
탑재된 GUI 類別值 사용으로 審查狀態 절차를 수정한 之後狀態 頂端值 항목은 構建全部 통과했다.

이번 實際資料 通信 검증의 범위는 **게스트와 QEMU 밖의 독립 宿主 程式 分隔條**第三操作數.
별도 물리 PC, 공인 인터넷 目的地址端點, SSH 터널, 實際資料 Pi 4 Ethernet에서의 송수신은 시험하지 않았다.
內核值 셸을 使用者 셸로 이식하거나 일반 프로세스 스케줄러를 추가한 변경은 아니다.
