# प्रयोगकर्ता 호출 경계

대상은 jkoros i386 ELF32다. Linux i386의 호출 번호와 바이너리 호환이 아니다. C의 cdecl 인수를 `मेशिन/सञ्चालनप्रणाली_कलहरू.s`에서 EAX(अनुक्रमणिका), EBX·ECX·EDX·ESI·EDI(첫째~다섯째 तर्क)로 변환한다. EBX·ESI·EDI·EBP를 보존하며 결과는 EAX다. कर्णेल_मान 실패는 음수 त्रुटि अनुक्रमणिका, C पुस्तकालय 실패는 -1과 양수 errno다.

커널은 0x04000000 이상, 0x04400000 미만의 प्रयोगकर्ता 영역 안에 자료의 전체 길이가 들어가는지 확인한다. 단순 널 검사가 아니다. C लगत 주소는 बाइट_मान 주소이며, 기존 Java AOT `int[]` 포인터와 혼용하지 않는다. Java फाइल 흐름의 어셈블리 경계가 별도 बाइट_मान 버퍼를 마련하여 같은 호출을 사용한다.

| अनुक्रमणिका | कार्य | तर्क |
|---|---|---|
| 30 | सिर्जना_फाइल | NUL 끝 नाम ठेगाना, सेटिङ, 허가 |
| 31 | 파일자료읽기 | 서술자, लगत ठेगाना, बाइट_मान 수 |
| 32 | लेख्नुहोस्_फाइल_लगत | 서술자, लगत ठेगाना, बाइट_मान 수 |
| 33 | बन्द_गर्नुहोस्_फाइल | 서술자 |
| 34 | खोज्नुहोस्_फाइल | 서술자, एनकोडिङ_मान 있는 अफसेट_मान, परियोजना_रूट |
| 35 | 파일서술자복제 | 서술자 |
| 36 | 파일서술자지정복제 | 서술자, 새 서술자 |
| 37 | 파일상태읽기 | 서술자, 48바이트 स्थिति_मान ठेगाना |
| 38 | हटाउनुहोस्_फाइल_प्रविष्टि_नाम | NUL 끝 नाम ठेगाना |
| 39 | सेट_फाइल_लम्बाइ | 서술자, 새 लम्बाइ_मान |
| 40 | 파일서술자제어 | 서술자, आदेश, मान |
| 41 | 통신종단점만들기 | ठेगाना सञ्चालनप्रणाली_मान, 종류, केस_मान अनुक्रमणिका |
| 42 | बाँध्नु_ठेगाना | 서술자, sockaddr_in ठेगाना, लम्बाइ_मान |
| 43 | 자료전문보내기 | 서술자, लगत ठेगाना, लम्बाइ_मान, सेटिङ, 요청 ठेगाना |
| 44 | 자료전문받기 | 서술자, लगत ठेगाना, लम्बाइ_मान, सेटिङ, 요청 ठेगाना |
| 45 | 통신주소읽기 | 서술자, sockaddr ठेगाना, socklen_t ठेगाना |
| 46 | 수신대기정하기 | 서술자, 0~2000 밀리초 |
| 47 | 파일저장확정 | 서술자 |

43번 요청은 32비트 주소와 32비트 길이의 두 칸이다. 44번 요청은 32비트 주소와 길이를 담은 32비트 값의 ठेगाना 두 칸이다. 수신 주소가 NULL이면 समान_मान ठेगाना 기록을 생략한다. sockaddr_in은 16바이트이며 ठेगाना 체계는 मोबाइल_मान बाइट_मान 차례, 접속번호와 IP 주소는 네트워크 बाइट_मान 차례다. 축소된 ठेगाना 버퍼에도 들어가는 앞부분을 쓰고 전체 ठेगाना आकार 16을 반환한다.

0~22번의 기존 Java AOT 호출은 유지한다. 0은 बाहिर_जानुहोस्_अनुप्रयोग, 2·3은 기존 तर्क 조회다. 현재 커널의 तर्क 목록이 कार्यान्वयन_गर्नुहोस्_आदेश 이름을 제외하므로 C 진입기는 argv[0]에 고정 स्ट्रिङ_मान `jkoros-app`을 넣고 이후 인수를 전달한다. argv 끝에는 NULL이 있다. 이 제한도 일반 UNIX प्रक्रिया_मान ABI와 다른 점이다.

표준 헤더의 पूर्ण_सङ्ख्या आकार, 플래그 मान, stat फाँट_मान 순서는 `स्रोत/포함/`에 정의한다. 동적 जडान·다중 प्रक्रिया_मान·스레드가 추가되면 त्रुटि अनुक्रमणिका 저장과 स्रोत_मान 수명, 호출 경계도 함께 검토해야 한다.
